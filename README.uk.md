## Про проєкт

**E-Pharmacy Backend** — окрема серверна частина адміністративної аптечної системи. REST API забезпечує захищену роботу з товарами, постачальниками, клієнтами, історичними замовленнями та показниками Dashboard, зберігаючи дані в MongoDB Atlas.

У репозиторії реалізовано модульний backend на Express. Готовий frontend до складу проєкту не входить. Опублікований сервер використовує погоджений оригінальний навчальний набір із **190 доменних документів**.

## Можливості

- JWT-автентифікація з незалежними серверними сесіями на одну годину та відкликанням поточної сесії
- Каталог товарів зі створенням, повним редагуванням і логічним видаленням
- Керування постачальниками із сумами EUR та збереженням історичних відомостей BDT
- Створення клієнтів, списки з пагінацією, редагування профілю через PATCH і підтверджена історія операцій
- Читання історичних замовлень зі збереженням їхніх знімків даних
- Dashboard із загальними лічильниками, окремою статистикою за 30 днів, п’ятьма останніми реєстраціями та фінансами за день
- Пошук імені як буквального підрядка; сортування товарів і замовлень; пагінація клієнтів
- Сувора валідація Zod, централізована обробка помилок і точні грошові значення Decimal128
- Явні значення null і метадані partial для неповних історичних даних
- Ідемпотентний імпорт із SHA-256, provenance та розмежуванням оригінальних і тестових даних
- Контракт OpenAPI та інтерактивна Swagger UI з Bearer Authorization

## API-ендпоїнти

| Метод | Ендпоїнт | Призначення | Bearer |
| --- | --- | --- | --- |
| POST | `/api/user/login` | Увійти та створити сесію | Ні |
| GET | `/api/user/user-info` | Отримати профіль користувача | Так |
| GET | `/api/user/logout` | Відкликати поточну сесію | Так |
| GET | `/api/dashboard` | Отримати показники Dashboard | Так |
| GET | `/api/products` | Знайти й відсортувати активні товари | Так |
| POST | `/api/products` | Створити товар | Так |
| PUT | `/api/products/{productId}` | Повністю замінити редаговані поля товару | Так |
| DELETE | `/api/products/{productId}` | Логічно видалити товар | Так |
| GET | `/api/suppliers` | Знайти постачальників | Так |
| POST | `/api/suppliers` | Створити постачальника | Так |
| PUT | `/api/suppliers/{supplierId}` | Повністю відредагувати постачальника | Так |
| GET | `/api/customers` | Знайти клієнтів із пагінацією | Так |
| POST | `/api/customers` | Створити клієнта із серверною датою реєстрації та нульовими витратами EUR | Так |
| GET | `/api/customers/{customerId}` | Отримати профіль і підтверджену історію клієнта | Так |
| PATCH | `/api/customers/{customerId}` | Частково змінити дозволені поля профілю | Так |
| GET | `/api/orders` | Знайти й відсортувати замовлення | Так |

Успішні відповіді мають формат `{ data, meta? }`, помилки — `{ error: { code, message, details? } }`. Створення повертає 201, вихід і видалення — 204 без тіла. Захищені операції потребують `Authorization: Bearer <token>`; відповідь 401 містить Bearer challenge. PUT вимагає всі редаговані поля, PATCH змінює лише передані дозволені поля профілю.

`POST /api/customers` вимагає `name`, `email`, `address` і `phone`; `country` необов’язкове (рядок або null, за замовчуванням null). Діють наявні правила тексту/email; повторювані email дозволені. Сервер установлює поточну дату реєстрації UTC, час створення/оновлення та точний початковий `spent` — нуль EUR у Decimal128. Фото й час імпорту дорівнюють null, import provenance відсутнє; обліковий запис для входу та історія покупок не створюються. Невідомі поля, зокрема фінансові, часові й технічні значення від клієнта, відхиляються.

Повні параметри, схеми та коди відповідей описано в [контракті OpenAPI](docs/openapi.json). Маршрути Swagger документують ці **16 бізнес-операцій**, а не додають нові бізнес-операції.

## Архітектура

Модулі в `src/modules/` розділяють маршрути, сервіси та моделі Mongoose. Zod перевіряє вхідні дані до звернення до бази, а спільні утиліти відповідають за DTO, гроші, UTC-періоди, повноту даних і помилки.

Доменні колекції: `products`, `suppliers`, `customers`, `orders`, `financialtransactions`. Автентифікація використовує `users` і `sessions`. JWT посилається на серверну сесію, а збережений хеш токена забезпечує її адресне відкликання. Публічних маршрутів реєстрації та refresh немає.

`src/openapi.ts` генерує `docs/openapi.json`; ця сама специфікація компілюється в сервер для Swagger. Докладні правила імпорту, категорій та історичних даних збережено в [технічному довіднику](docs/backend-reference.md).

## Встановлення та запуск

Потрібні Node.js **26.x** (контрольна версія **26.13.0**), npm, Git і власна MongoDB 8.x для розробки.

Для нового клону:

```bash
git clone https://github.com/AvalianY/admin_dashboard_back.git
cd admin_dashboard_back
npm ci
```

Після цього створіть `.env` на основі `.env.example`: `cp .env.example .env`, у PowerShell — `Copy-Item .env.example .env`. Налаштуйте **окрему базу для розробки**, випадковий JWT_SECRET довжиною щонайменше 32 символи та точний список дозволених origins. Production-підключення не слід використовувати для локальних тестів.

Для одноразової ініціалізації облікового запису задайте власні реальні INITIAL_USER_* локально. Пароль вводьте приховано в середовище процесу та прибирайте після команди; не зберігайте його у файлах проєкту. Наявний обліковий запис не перезаписується. Деталі: [технічний довідник](docs/backend-reference.md).

```bash
npm run user:init
npm run seed:demo
npm run dev
```

```bash
npm run build
npm start
```

## Імпорт даних

Джерела даних навмисно розділені:

| Джерело | Команда | Використання |
| --- | --- | --- |
| `v1` | `npm run seed` | Оригінальний навчальний набір із локального ігнорованого data/source/; production e_pharmacy, 190 документів |
| `demo-v1` | `npm run seed:demo` | Детерміновані синтетичні дані з data/demo/; лише розробка та ізольовані тести |

Імпорт перевіряє окремий маніфест і SHA-256, зберігає всі рядки джерела разом із дублікатами та надає унікальний provenance. Повторний імпорт того самого набору не додає документів і не перезаписує зміни користувача. Тому `seed` **не замінює відновлення з резервної копії**. Оригінальні JSON не завантажуються до GitHub або Render.

Production містить 60 товарів, 5 постачальників, 88 клієнтів, 25 замовлень і 12 фінансових операцій. Невідомі історичні значення залишаються невідомими; BDT не конвертується в EUR за вигаданим курсом. `seed:demo` не можна запускати для публічної production-бази.

## Документація Swagger

Локально: [http://localhost:3000/api-docs](http://localhost:3000/api-docs). Інтерфейс показує всі 16 операцій за модулями, параметри, приклади запитів і відповідей, схеми та HTTP-коди. JSON-специфікація доступна за `/api-docs/openapi.json`. Усі приклади синтетичні.

1. Відкрийте потрібний модуль та операцію.
2. Виконайте Login зі своїми обліковими даними й отримайте токен.
3. У **Authorize** введіть лише значення токена для наявної Bearer-схеми.
4. Увімкніть **Try it out** і свідомо виконайте запит.
5. Завершіть поточну сесію через Logout.

Токени не зберігаються після перезавантаження сторінки чи між сесіями браузера. Операції запису змінюють обрану базу, тому для production потрібне окремо погоджене тестове вікно з backup і відновленням. Для браузерних запитів точний origin API має бути дозволений у CORS_ORIGINS; усі захищені операції й надалі потребують JWT.

Публічна Swagger UI: [https://e-pharmacy-api-kz62.onrender.com/api-docs/](https://e-pharmacy-api-kz62.onrender.com/api-docs/). Інтерактивна документація розгорнута на Render із наявною Bearer-схемою. Локальне розширення створення клієнтів збільшує контракт до 16 операцій; його публікація в GitHub і Render потребує окремого дозволу. Новий POST ще не слід вважати доступним у production.

## Розгортання

Наявний API працює за адресою [https://e-pharmacy-api-kz62.onrender.com](https://e-pharmacy-api-kz62.onrender.com) на **Render Free у Frankfurt** з **MongoDB Atlas Free на AWS Frankfurt**. Кореневий маршрут може повертати 404; бізнес-операції захищені.

`render.yaml` задає Node 26.13.0, `npm ci --include=dev && npm run build`, `npm start` та вимкнені автоматичні deployment. Після підключення до БД сервер слухає `0.0.0.0` і наданий PORT. Секрети налаштовуються в приватних environment settings; ініціалізація та імпорт не виконуються в build/start hooks.

Render Free зупиняє неактивні сервіси; наступний запит може спричинити cold start. Дані та сесії зберігаються в Atlas, локальна файлова система сервісу тимчасова. [Безкоштовні ліміти](https://render.com/docs/free). `render.yaml` дозволяє лише `https://e-pharmacy-api-kz62.onrender.com` як production-origin для Swagger. Фактичні Render Environment Settings мають відповідати цій конфігурації: локальна зміна YAML не оновлює наявний сервіс автоматично. Frontend-origin буде додано лише після його погодження.

Порядок дій, безпечне адміністрування та межі дозволів: [інструкція розгортання](docs/free-deployment.md). Нові кроки публікації погоджуються окремо.

## Тестування та якість

Публічні тести запускають власні тимчасові MongoDB та працюють із синтетичними fixtures, без приватних оригіналів. `test:source` перевіряє оригінали окремо й не пропускає перевірку за відсутності файлів. Тести не запускаються проти Atlas.

Набір перевіряє автентифікацію, сесії, каталоги, Dashboard, імпорт, контракти запитів/відповідей, помилки та фактичний скомпільований сервер. Перевірки Swagger охоплюють HTML, локальні ресурси, всі 16 операцій, приклади, Bearer-схему, налаштування збереження токенів і незмінні межі CORS/JWT. Тести створення клієнта використовують ізольовану MongoDB та перевіряють валідацію, межі UTC, Decimal128, пагінацію по п’ять записів, редагування профілю, Dashboard і збереження наявних документів.

**Live-підтвердження від 13.11.2026:** усі 15 бізнес-операцій, 74 HTTPS-запити та точне відновлення 190 оригінальних документів після тимчасових тестових змін — PASS. Раніше також перевірено 49 безпечних HTTPS-сценаріїв, зокрема cold start. Публічну Swagger UI та її OpenAPI JSON перевірено після розгортання: обидва ресурси повертають HTTP 200; специфікація містить усі 15 операцій і наявну Bearer-схему.

Локальні перевірки розширення створення клієнтів пройдено: TypeScript, ESLint, production build, **200 публічних тестів** та **5 окремих тестів оригінальних даних**; `npm audit` повідомляє про **0 відомих вразливостей**. Окремий браузерний тест скомпільованого сервера показує всі 16 операцій Swagger і перевіряє нове тіло запиту, задокументовану відповідь 201, передавання Bearer та очищення авторизації після перезавантаження. Його тестовий токен очікувано дає 401 без підключення до БД; коректне створення перевіряють integration тести в ізольованій MongoDB. Production-приймання нової операції ще не виконано.
